# Mobile Application Hosts and GPU Smoke Paths

Last reviewed: 2026-11-20

## Scope and evidence

StormEngine has minimal native application hosts for Android and iOS. Both hosts now include a native GPU clear-and-present smoke path. They validate platform integration, surface acquisition, command submission, and presentation at build level; they are not complete game runtimes or Scene renderers.

| Platform | Artifact | GPU path | Current boundary |
|---|---|---|---|
| Android | arm64-v8a debug APK | Vulkan 1.0: Android surface, swapchain, clear render pass, command submission, and presentation | Clear-only frame while NativeActivity is active; no SpriteBatch/mesh draw, shader pipeline, texture upload, or Core GameLoop integration |
| iOS | unsigned arm64 device .app bundle | Metal: CAMetalLayer drawable, MTLCommandQueue, render-pass encoder, clear, and present | Clear-only frame driven by CADisplayLink while the app is active; no SpriteBatch/mesh draw, shader/material pipeline, or Core GameLoop integration |

GitHub Actions cross-compiles the Android and iOS GPU translation units and builds their host packages. No physical-device or simulator runtime execution has been performed. Neither platform is Device-Verified.

## Android host

The Gradle project is under `platforms/android`.

Toolchain selected for the host build:

- JDK 17
- Gradle 9.6.0
- Android Gradle Plugin 9.4.0
- Android SDK 36 / Build Tools 36.0.0
- Android NDK 28.2.13676358
- CMake 3.31.0
- arm64-v8a
- minSdk 24 and targetSdk 36

API 24 is required by this initial Vulkan path because the Android Vulkan loader is available from API 24. The NDK cross-build must therefore use `ANDROID_PLATFORM=android-24`, matching the Gradle package's `minSdk 24`. Devices without a compatible Vulkan implementation are not yet covered by an alternate backend.

Build a debug APK after installing those SDK packages and Gradle:

```sh
gradle -p platforms/android :app:assembleDebug
```

Expected artifact:

```text
platforms/android/app/build/outputs/apk/debug/app-debug.apk
```

The manifest launches `android.app.NativeActivity` and loads `storm_android_native_activity`. While a valid native window is attached, the NativeActivity creates a `VulkanClearRenderer`, which owns the `ANativeWindow` reference, Vulkan instance/surface, selected graphics-and-present queue, logical device, swapchain, image views, clear render pass/framebuffers, command pool/buffer, semaphores, and frame fence. The loop polls at a bounded 16 ms interval only while lifecycle state permits execution. Resize recreates swapchain-dependent resources; the renderer is destroyed before the native window is detached.

This slice records a real Vulkan clear-only frame. It does not draw `SpriteBatch` output, upload textures, compile shaders, build a reusable engine GraphicsDevice, connect Runtime::MobileFrameDriver/Core::GameLoop, or export a game. Vulkan device-loss recovery and a non-Vulkan fallback remain unimplemented. The APK is a development host shell only; release signing, AAB generation, icon/splash configuration, and wider ABI support remain planned.

## iOS host

The iOS host target is `storm_ios_app`, generated by the root CMake project. It uses the existing `StormEngineSceneDelegate` and a root UIKit controller whose view layer is `CAMetalLayer`. The controller maps view bounds and contentScaleFactor to a checked pixel extent, maintains the shared SurfaceLifecycle metadata, and forwards UIKit touch lifecycle callbacks to TouchInput.

The controller also creates a Metal device and command queue. A `CADisplayLink` drives a small render callback while the application is active: it acquires the next CAMetalLayer drawable, creates a render-pass descriptor, clears the drawable texture, encodes the command buffer, presents the drawable, and commits the command. This is a clear-and-present smoke path, not a Sprite/Mesh renderer. It does not draw Scene content, compile/load engine shaders, upload textures, connect to the Core GameLoop, or provide device-loss/resource-recreation policy beyond normal drawable acquisition.

Build the unsigned device app bundle on macOS with Xcode and the iOS SDK:

```sh
cmake -S . -B build-ios-arm64 -G Xcode \
  -DCMAKE_SYSTEM_NAME=iOS \
  -DCMAKE_OSX_ARCHITECTURES=arm64 \
  -DCMAKE_OSX_DEPLOYMENT_TARGET=13.0 \
  -DSTORMENGINE_BUILD_TESTS=OFF \
  -DCMAKE_BUILD_TYPE=Release

cmake --build build-ios-arm64 --config Release --target storm_ios_app
```

Expected bundle:

```text
build-ios-arm64/Release-iphoneos/storm_ios_app.app
```

Code signing is disabled for CI. There is no provisioning profile, archive, IPA, or distribution workflow. The host build checks Objective-C++/UIKit/Metal compilation and packaging only. Real-device drawable acquisition, frame pacing, resize/rotation, background/foreground transitions, thermal behavior, and battery impact remain unverified.

## Security and compatibility notes

- Signing certificates, provisioning profiles, keystores, and private keys must remain outside the repository.
- The Android package is restricted to arm64-v8a for this first build target; this is not support for every Android device.
- Android's minSdk/API 24 requirement belongs to the current Vulkan smoke path; any lower-API support requires an explicitly designed fallback and separate validation.
- The iOS app target uses iOS 13.0 because the existing scene lifecycle adapter is based on `UIWindowSceneDelegate`.
- The host package SDK/deployment settings are build configuration, not a complete engine compatibility policy.
- Successful compilation and packaging prove build integration only. Surface lifecycle, native touch delivery, actual GPU presentation, swapchain/drawable recreation, frame pacing, thermal behavior, and battery impact still require simulator/device tests.

## Next integration steps

1. Connect native frame timing and application lifecycle to `Storm::Runtime::MobileFrameDriver` without duplicating the existing host-side lifecycle model.
2. Introduce the backend-neutral GraphicsDevice/resource/command contracts, then connect SpriteBatch and RenderGraph execution to native Vulkan/Metal implementations.
3. Add shader, texture-upload, and GPU draw tests, and validate clear/present plus resource recreation on physical Android and iOS devices.
4. Add release signing and export only after runtime integration and compatibility policy are ready.
