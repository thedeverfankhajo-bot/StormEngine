# StormEngine

StormEngine is an early-stage, mobile-only game-engine project targeting **Android and iOS**. Its intended game models are 1D, 2D, and 3D. The editor is also intended to run only on mobile devices.

> **Current status: C++ foundation, Android/iOS lifecycle adapters, fixed-step Core loop, lifecycle-aware Mobile Runtime frame driver, and a generation-safe Scene/Entity hierarchy, separate Transform2D and Transform3D math/scene-transform layers, and a bounded versioned Scene archive with explicit component codecs and built-in Transform1D/Transform2D/Transform3D codecs, plus an initial scalar 1D physics world.** The platform-neutral C++ foundation cross-compiles for Android arm64 and iOS device arm64. An Android NativeActivity entry point maps lifecycle and native-window metadata into the platform contracts and is compiled/linked as a shared library in CI. The Core module now provides a frame coordinator that runs input, events, bounded fixed updates, variable update, and render callbacks in a defined order. Core also contains a synchronous, exact-type event dispatcher with move-only RAII subscriptions and explicit handler-error propagation. The repository now contains a minimal Android arm64 debug APK host and an unsigned iOS device app-bundle host. These shells exercise native application packaging and lifecycle entry points only. They are not a complete runtime: A Runtime TouchInputGameLoopAdapter now provides a tested frame-scoped handoff into GameLoop::process_input; the Android/iOS host shells do not yet instantiate a gameplay consumer or native frame source. Native gameplay integration of portable gesture/action mapping, a renderer, 3D physics, a complete 1D gameplay runtime, editor, asset importer, and release export pipeline remain unimplemented. Do not mistake a packaged host shell or frame coordinator for a usable game engine. The 2D foundation now includes independent planar transforms, an independent Physics2D library with bounded spatial-hash broadphase and circle/axis-aligned-box contacts, and an optional PhysicsScene2D bridge to Scene entities. It now includes platform-neutral Camera2D view/projection math and a `Storm::Rendering2D` CPU submission slice that collects Scene sprites, composes full Transform2D ancestry, validates UV and transform data, and emits bounded indexed quads while preserving painter order. A camera-aware collection overload now applies Camera2D view-projection into normalized device coordinates; this is still CPU-side submission, not a GPU renderer: Metal/Vulkan devices, shaders, texture uploads, draw calls, and frame presentation are still absent. Camera viewport lifecycle integration, animation, and editor workflows also remain unimplemented. The initial 1D physics slice is host-tested/target-built separately from any renderer; it is not yet a complete 1D gameplay runtime.

## Product constraints

- Runtime targets: Android and iOS only.
- Editor targets: Android and iOS only.
- Host operating systems may be used for engineering, CI, cross-compilation, and host-side tests; they are not product targets.
- All repository development is performed on main.
- Platform and graphics capabilities are reported only after implementation and validation on real target devices.

## Current foundation

- C++20 and CMake project configuration.
- Typed Error and Result<T> value types.
- A platform-neutral, injectable logging interface.
- An atomic byte-budget accounting utility. It accounts for reservations; it does not allocate memory.
- A minimal engine initialization/shutdown state model. It does not initialize an operating-system runtime.
- A fixed-step scheduler that accumulates elapsed nanoseconds, caps accepted frame deltas and per-frame catch-up work, reports discarded backlog, and provides a render interpolation alpha. It does not own a clock.
- A callback-driven Core game-loop coordinator with deterministic phase order: input, events, fixed updates, variable update, and render. It accepts elapsed time from its caller and remains independent of Android/iOS APIs.
- A separate Runtime MobileFrameDriver that gates Core callbacks on foreground-active lifecycle and an attached surface, detects lifecycle revisions and surface generations, validates monotonic timestamps, and resets simulation timing after suspension or surface recreation.
- A synchronous Core event dispatcher keyed by exact C++ event type, with ordered handlers, move-only RAII subscriptions, mutation-safe dispatch snapshots, and propagated handler errors.
- An initial Core Scene/Entity system with non-reused Scene IDs, generation-checked entity handles, scene-local typed component storage, automatic component cleanup, and a validated parent/child hierarchy. It is not yet an archetype ECS and has no reflection, automatic component discovery, or editor integration.
- A separate Math target with finite-value checks, normalized quaternions, axis-angle construction, column-major 4x4 matrices, and a tested 3D geometry slice (AABBs, spheres, planes, normalized rays, and ray intersections). Core TransformSystem composes optional local Transform3D components through the entity hierarchy on demand.
- A separate Serialization target with bounded little-endian binary primitives and a version-1 Scene archive. Component payloads require explicit stable identifiers and schema-versioned codecs; Transform3D has a built-in codec. Serialization is in-memory only and does not perform filesystem I/O.
- An optional `Storm::Physics1D` target with scalar body state, generation-checked world-local handles, Static/Kinematic/Dynamic bodies, semi-implicit Euler gravity/force integration, impulses, 1D interval contacts, filtered closed-interval overlap queries, nearest-hit scalar raycasts, persistent Begin/Stay/End contact events, triggers, collision masks, restitution response, and transactional bounded steps. Contact history is generation-aware and advances only after a successful step. It is discrete, single-thread-affine, and uses a bounded O(n²) pair scan; no 2D/3D physics or renderer exists yet.
- An optional `Storm::PhysicsScene1D` adapter connects Physics1D bodies to Scene entities through scalar `Transform1D` components. It is separate from Core and Physics1D; it explicitly synchronizes successful fixed steps and retires stale entity/component mappings. It is single-thread-affine; its nine host tests and Android/iOS target builds passed in CI run [41340647156](https://github.com/thedeverfankhajo-bot/StormEngine/actions/runs/41340647156).
- An optional `Storm::Physics2D` target is independent of Physics1D, Core, Scene, and platform SDKs. Its bounded fixed-step world supports Static/Kinematic/Dynamic bodies, circle and axis-aligned box colliders, gravity, forces/impulses, restitution, bounded friction impulses, triggers, symmetric layer/mask filtering, and a uniform spatial-hash broadphase with canonical candidate-pair ordering. Simulation steps use temporary state and commit only after integration, broadphase, narrow phase, collision response, and resource-budget checks succeed. Read-only overlap queries and nearest-hit raycasts support the same Circle/AABB shapes, stable slot ordering, layer masks, and optional trigger filtering; queries scan the bounded body set. It is single-thread-affine and now provides persistent Begin/Stay/End contact events whose generation-aware history advances only after successful steps; rotated shapes, capsules/polygons/edges, CCD, sleeping, and rendering remain unimplemented. The optional `Storm::PhysicsScene2D` adapter connects unparented entities through `Transform2D::translation`, preserving rotation/scale without applying them to collider geometry. See [2D Physics](docs/PHYSICS-2D.md) and [ADR-0012](docs/ADR-0012-PHYSICS-2D-SCENE-INTEGRATION.md).
- A separate `Storm::Rendering2D` target collects `Sprite2DComponent` values from Scene, composes full Transform2D ancestry, validates sprite/UV data, and builds bounded four-vertex/six-index quad geometry. It preserves painter order and only batches adjacent sprites with the same texture key; the key is an opaque batching identifier, not a GPU resource. Ten host tests cover geometry, pivot/rotation, sorting, contiguous ranges, validation, capacity, Scene hierarchy, failure cleanup, and object lifetime. No graphics API, shader, texture upload, draw call, or presentation backend is implemented yet.
- A portable `Storm::Input` target ingests bounded multi-pointer Down/Move/Up/Cancel events, tracks logical coordinates and per-frame deltas, validates monotonic timestamps and surface generations, and reports explicit cancellation. Android NativeActivity MotionEvent callbacks and the iOS host view's UIKit touch callbacks now feed this state, including Android pixel-to-point conversion and focus/surface cancellation. The Runtime adapter exposes immutable per-frame touch events and active-pointer state to an application consumer. A platform-neutral GestureRecognizer now interprets Tap, DoubleTap, LongPress, Drag, Swipe, two-pointer Pan, and Pinch with bounded output and surface/timestamp validation. A portable InputActionMap now maps recognized gesture streams to stable 32-bit action IDs with lifecycle phases, atomic rebinding, and bounded output. The Runtime GestureActionGameLoopAdapter now forwards non-empty action batches to an application-owned game-action consumer in the GameLoop input phase; the Android/iOS host shells still do not instantiate a gameplay consumer or native frame source.
- Explicit timing reset for lifecycle suspension/resume; the platform runtime must decide when a frame may run.
- A platform-neutral lifecycle state machine with validated transitions.
- A bounded, allocation-free, multi-producer/single-consumer lifecycle event queue with explicit full/closed results.
- A platform-neutral surface lifecycle contract with validated dimensions/scale and generation-based stale-callback rejection. Logical point sizes are converted to checked pixel extents by a shared helper.
- Android NativeActivity maps native-window metadata into the surface contract without retaining an ANativeWindow pointer. The iOS host view maps UIView bounds and contentScaleFactor into the same contract and tracks attach/resize/detach generations; this is metadata-only and does not create GPU resources.
- A platform-neutral iOS scene-event adapter plus an Objective-C++ StormEngineSceneDelegate available on iOS 13+ that consumes UIKit scene callbacks, owns one lifecycle state machine per scene, and exposes an overridable transition hook to the host runtime. Its source is compiled only for the iOS target.
- Host tests for Foundation, Math, Core, Scene, Serialization, Input, Physics1D/2D, platform lifecycle, and Runtime integration. The current host CMake configuration registers twenty-six CTest executables. The PhysicsWorld2D executable contains twenty-eight named world cases, including overlap, raycast queries, and persistent contact transitions; PhysicsScene2D has eleven adapter cases. CI validates all twenty-six CTest executables under GCC, Clang, Apple Clang, and Clang ASan/UBSan; Clang Static Analysis and Android/iOS target builds run for main-branch changes.
- CI cross-compilation of Foundation, Math, Physics1D, Physics2D, Input, Core, Serialization, Platform, and Runtime libraries for Android arm64-v8a and iOS device arm64; the built-in Transform3D SceneSerializer path is explicitly instantiated in both mobile builds. Android NativeActivity shared-library compilation/linking is also checked.

The standalone Android NDK cross-build uses ANDROID_PLATFORM=android-21. The Android debug host APK is configured for arm64-v8a, minSdk 21, and targetSdk 36; these are host-package settings, not a broad engine compatibility guarantee. The iOS host target uses the iPhoneOS Device SDK with an iOS 13.0 deployment target and produces an unsigned app bundle. Neither job signs a release or creates an AAB/IPA.

The Android bridge is an event/lifecycle and native-touch adapter. It is not yet wired to the Runtime MobileFrameDriver or Core gameplay input phases and does not provide frame pacing, rendering, sensor access, low-memory policy, or Java/Kotlin UI. The iOS UIKit touch adapter likewise updates host-owned TouchInput state but is not connected to Core gameplay. The APK packages this bridge as a native host shell only. MobileFrameDriver accepts monotonic timestamps supplied by a future native frame source; neither Android Choreographer nor iOS CADisplayLink is integrated. The iOS scene delegate and UIView surface-metadata adapter are compiled into the unsigned host app, but neither is connected to a complete game runtime. No renderer, 3D physics implementation, complete iOS runtime, signed iOS app, release APK/AAB/IPA pipeline, or physical-device runtime validation exists. The Android debug APK and unsigned iOS app bundle are packaging checks, not device-runtime verification. The first 1D physics model is a discrete host-side simulation library and has no rendering/input/device integration.

## Mobile application host shells

The Android Gradle project packages the existing NativeActivity bridge into an arm64 debug APK. The iOS CMake target creates an unsigned device app bundle and uses the existing UIKit scene lifecycle adapter. Both are minimal host shells; neither is a game runtime, editor, renderer, or store-release pipeline. See [Mobile App Hosts](docs/MOBILE-APP-HOSTS.md) for exact build commands and limitations.

## Build and test the host foundation

Requirements: CMake 3.24 or newer, Ninja for the preset workflow, and a C++20 compiler.

    cmake -S . -B build -DSTORMENGINE_BUILD_TESTS=ON
    cmake --build build --config Debug
    ctest --test-dir build --output-on-failure

Host-side test binaries are engineering tools only; they are not supported StormEngine runtime targets or editor targets.

## Architecture direction

The engine core will remain independent of editor UI, platform lifecycle headers, and rendering APIs. Android and iOS integrations will sit behind explicit platform interfaces. Rendering backends will be selected based on the capabilities of each mobile platform and device; no single graphics API is assumed to be universally available.
